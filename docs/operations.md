# Эксплуатация и проверки

## Лимиты и нагрузка

Облачный Telegram Bot API позволяет `getFile` до 20 MB. Бот применяет минимум
из лимита тарифа и cloud cap при приёме и после ожидания очереди: Free (15 MB)
упирается в свой лимит, Pro (`max_size_mb: 0`) — в облачные 20 MB. В локальном
режиме (`api.local: true`) потолок снимается и Pro не ограничен ничем.

Лимит тарифа выше облачного потолка не действует: при старте бот пишет
предупреждение (`plans.pro.max_size_mb: 200 MB не действует — ...`), но
запускается. Значение `0` означает «без ограничения» и предупреждения не даёт.

Отдельный и меньший лимит — на РЕЗУЛЬТАТ: Telegram принимает видео-сообщение
(«кружок») не больше 12 MB (`services.conversion.VIDEO_NOTE_MAX_BYTES`), тогда
как `getFile` отдаёт до 20 MB. Поэтому высокое качество на Pro (640×640) и длинный
фрагмент вместе могут дать кружок тяжелее 12 MB, и API отвергает отправку
(`file of size … is too big for a video note`). Бот считает размер результата
после кодирования и до отправки: перетяжелённый кружок не загружается зря,
пользователь получает причину и подсказку — снизить качество в ⚙️ Настройки
(называется доступное разрешение ниже) или обрезать видео короче `/fragment`.
Тот же отказ, пришедший от API на отправке, распознаётся и показывается так же,
а не общим «ошибка конвертации».

На 1 CPU / 512 MB оставьте `processing.workers: 1`. `queue_size` ограничивает
ожидающие пачки, а не только работу одного пользователя. Переполненная очередь
отказывает без расходования квоты. Позиция — снимок при приёме, не прогноз времени.
Запросы одного пользователя по-прежнему сериализуются, права и квота перечитываются.

`probe_timeout_sec` ограничивает ffprobe, `encode_timeout_sec` — ffmpeg.
Отмена завершает дочерний процесс и дожидается его. При остановке сначала
заканчиваются принятые задачи, после общего `shutdown_timeout_sec` остаток отменяется.
Compose оставляет процессу 45 секунд до SIGKILL; увеличивайте этот запас при
увеличении shutdown timeout. Незавершённая очередь не сохраняется после аварии.

## Кадрирование, фрагмент и повторная выдача

Настройки пользователя сохраняются в SQLite. `crop` обрезает края по центру;
`fit` сохраняет кадр целиком с полями. По умолчанию длинный исходник отклоняется:
для него выберите фрагмент, например `/fragment 01:20 30`. Эта настройка действует
на последующие видео до `/fragment reset`; начало за пределами видео — ошибка.
Выходной кружок не превышает лимит тарифа и Telegram (60 секунд).

Кэш хранит Telegram `file_id`, а не локальную копию видео. Ключ включает
`file_unique_id`, кодирование, кадрирование и выбранный фрагмент. Если Telegram
отклоняет закэшированный идентификатор, бот выполняет обычную конвертацию.
Успешная повторная выдача считается в квоте, как и новая конвертация.

## Собственный Bot API для файлов больше 20 MB

Это опциональный режим, сервер автоматически не разворачивается. Нужен официальный
[telegram-bot-api](https://github.com/tdlib/telegram-bot-api), запущенный с `--local`,
и собственные api_id/api_hash от Telegram. Не добавляйте эти значения в репозиторий.
При переходе следуйте официальной процедуре `logOut` с облачного сервера.
Не выполняйте её, пока не готовы переключить рабочий бот.

В YAML задайте `api.local: true` и `api.base_url: "http://bot-api:8081"`.
Затем можно увеличить `plans.*.max_size_mb`. URL содержит только origin, без токена,
credentials и пути. Сервер должен быть доступен только в доверенной сети.

В local-режиме aiogram читает абсолютный `file_path`, возвращённый сервером.
Каталог файлов Bot API должен быть доступен боту по ТОЧНО ТОМУ ЖЕ абсолютному пути:
для Docker смонтируйте общий volume в оба контейнера. Обычный volume для временных
конвертаций не заменяет это общее хранилище. Без него скачивание локального файла
не заработает, даже если `getFile` успешно отвечает. Рабочий local-сервер и реальные
загрузки требуют отдельной проверки на вашей инфраструктуре.

## Платежи и поддержка

Снимки новых счетов в `issued_invoices` сохраняют первоначальную цену и пользователя.
`payments.applied_expires` фиксирует исполнение независимо от последующей отмены
подписки. Транзакция откатывает оплату и выдачу вместе; повтор доставки безопасен.
Старые зарегистрированные, но не исполненные оплаты восстанавливаются при повторной
доставке. Автоматическая отправка запроса возврата или изменение баланса не выполняются.

`/paysupport описание` пересылает обращение всем администраторам. Администратор
отвечает `/supportreply ID текст`. Пользователь получает сообщение от бота.
Обращения записываются в `support_requests` (только `user_id` и время), и по этому
журналу работают лимиты против спама: `support.cooldown_sec` — пауза между
обращениями (по умолчанию 120 с) и `support.daily_limit` — обращений в сутки
(по умолчанию 3, `0` снимает лимит). Проверка идёт под per-user блокировкой, поэтому
десять одновременных `/paysupport` не дают десять сообщений админам; запись делается
до отправки, так что недоставленное обращение не возвращает квоту. Вызов команды без
текста лишь показывает инструкцию и квоту не тратит. Возврат Stars по-прежнему
рассматривает администратор; отмена Pro сама по себе
не возвращает оплату. Перед публикацией проверьте тексты `/terms` применительно
к вашей юрисдикции и оператору сервиса.

## Подсказки команд

Меню «/» в клиенте Telegram строится из списков, записанных на серверах Telegram.
Их публикует бот при старте (`command_hints.py`): базовый список — в `default` и
`all_private_chats`, расширенный с админскими командами — в scope личного чата
каждого `bot.admin_ids`, по три языковых варианта (`без language_code`, `ru`, `en`).
`all_private_chats` заполняется вместе с `default`, потому что он приоритетнее и
оставшееся от ручных настроек значение перекрыло бы `default+ru`.

Публикация не влияет на запуск: ошибки логируются, недоступный админ (например, не
открывал бота — `chat not found`) пропускается, остальные применяются. `/syncmenu`
повторяет публикацию вручную и сообщает, кому не удалось. В BotFather `/setcommands`
после этого заходить не нужно — он пишет в то же хранилище и затрёт список.

## Тексты о тарифах

`plan_copy.py` собирает обе подсказки о тарифах из конфига: `pro_benefits` (блок
«что даёт Pro» на экране подписки для Free-пользователя) и `tariff_summary`
(сводка в `/help`). Значения берутся из `plans` и `APIConfig.input_limit_bytes`,
а строка добавляется только если тарифы действительно различаются — поэтому
изменение лимитов в `config.yaml` сразу меняет текст, и реклама Pro не может
разойтись с реальностью. Экрану Pro апселл не показывается.

## Healthcheck и секреты

`python healthcheck.py` проверяет свежий heartbeat приложения, существование PID
и чтение SQLite. Новый процесс Python сам по себе не делает бот healthy.
Heartbeat появляется после успешной инициализации и `getMe`, исчезает при остановке.
Это проверка живого приложения и БД, не постоянный тест доступности Telegram.

В Docker нет рабочего `config.yaml`: он исключён из context, а Dockerfile
явно копирует только `config.example.yaml`. Конфиг подаётся через read-only bind mount.
Старые опубликованные образы могут содержать токен — новые правила не чистят их слои.

## Проверки без рабочего Telegram и БД

Используйте Python 3.12, как в образе:

```bash
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements-dev.txt
pytest -q
ruff check .
mypy .
docker compose config --quiet
docker build -t video-circle-check:local .
```

Реальные ffmpeg-тесты создают короткие видео: без звука, с поворотом и нестандартным
SAR, с разными пропорциями и повреждённые. Платёжные регрессии используют временную
SQLite и намеренные ошибки транзакции; concurrency-тесты проверяют продления,
lifetime и создание пользователей. Тесты не запускают polling с рабочим токеном.

Временные файлы лежат в отдельном `processing.temp_dir`; cleanup не сканирует общий
системный `/tmp`. Директории активных задач защищены, исходники удаляются после работы.
SQLite перед обновлением резервируйте штатным online backup API или после остановки.
